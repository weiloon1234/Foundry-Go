## Typed public contracts

Generate model-specific create/patch drafts with field-aware getters, setters and assignment state. Hooks receive the concrete model/draft and a transaction-bound context. Observers receive typed before/after snapshots. Do not expose generic database records as the ordinary lifecycle interface.

Generated draft getters/setters already exist from milestones 03/05. Preserve their immutable `Set`, nullable `Clear`, and omission-preserving `Unset` behavior when integrating hooks. Regular model structs retain exported Go fields; domain computed getters may be ordinary typed Go methods. Field reads and in-memory assignment must not perform hidden database I/O.

Change sets must distinguish assigned fields from changed stored values. Compare the locked pre-write snapshot with the fully hydrated write result after mutators and database defaults/triggers; assigning an email that normalizes to its existing value is assigned but unchanged. A missing model snapshot on creation/deletion is distinct from a present model's NULL field. Keep stored snapshots separate from read-accessor output. Reuse codec canonical representations for comparison, preserving interval months, days and elapsed components instead of reusing the SQL-equivalence key used by relation grouping. Cover equivalent JSON/decimal/instant representations, interval component changes, omitted defaults and explicit zero/NULL in the change-tracking consumer tests.

Deliver Laravel-style read accessors and write mutators with concrete field input/output types and ordinary errors. Custom read accessors are explicit typed getter methods: fetching a model preserves its stored fields, and evaluating a getter does not replace them. This is the user's agreed choice and matches Rust Foundry's explicit accessed-value methods. Preserve stored IDs, relation keys, pagination keys, credential hashes and lifecycle snapshots. Write mutators run once in the normal write pipeline, followed by final value validation. Generated field-aware discovery must reject an incompatible model or field value type. Neither accessor/mutator dispatch nor hook drafts should require field-name strings or `any` in normal application code. The public guides document the concrete generated signatures alongside compiling consumer examples.

This includes Laravel's `setEmailAttribute` behavior, not only generated draft setters. The first implementation increment supplies the following automatic method convention; its public guide and verification status are linked below:

```go
func (User) MutateEmail(email string) (string, error) {
    return strings.ToLower(strings.TrimSpace(email)), nil
}
```

Normal `Create` and `Update` must invoke a registered field mutator automatically; consumers must not call it manually in handlers. A draft retains its supplied value until persistence: transformation runs once after the before-write hooks and before SQL, with validation of the transformed value. Run field mutators only for assigned fields, including assignments added by a hook; an omitted patch field remains unchanged. Nullable fields preserve explicit NULL rather than replacing it with a scalar zero value. A mutator error aborts the write transaction. Explicit set-based bulk operations retain the separate lifecycle semantics defined below.

Example inside a user-creating hook receiving `draft *UserDraft`. Existing generated setters return a new value, so hooks must assign it back:

```go
if !draft.IntroducerID().IsSet() {
    *draft = draft.SetIntroducerID(defaultIntroducer.ID)
}
```

Typed event descriptors retain payload type through registration and dispatch. Event keys are declared once and carry a schema version for durable serialization. Audit and origin contracts live below auth integration so events/database do not import the auth implementation.

## Lifecycle order and transactions

For create: `saving -> creating -> write mutators -> INSERT -> created -> saved`.

For update: `saving -> updating -> write mutators -> UPDATE -> updated -> saved`.

The pre-hooks can inspect and modify typed drafts or return errors. Revalidate final values after hooks/mutators. Post-write hooks run inside the same transaction and can still fail the unit of work. `retrieved` runs after stored-model hydration, outside a write transaction unless the read used one. Retrieval does not invoke custom getters or replace stored fields; getter evaluation is a separate explicit call.

Soft deletion uses `deleting -> soft-delete write -> deleted`; restoration uses `restoring -> restore write -> restored`; force deletion uses `forceDeleting -> deleting -> DELETE -> deleted -> forceDeleted`. Each event distinguishes the operation kind. These special operations do not implicitly emit saving/updating events as well.

After-commit observers run only after the outer transaction commits. Savepoint rollback discards callbacks/outbox entries created within that savepoint. Callback errors cannot roll back committed data and must be reported as post-commit errors, not ordinary write failures.

### Managed timestamps and application time

Managed timestamps now use the framework's existing write pipeline. The [consumer guide](../docs/guides/model-timestamps.md) documents these contracts:

- Recognize the persisted Go fields `CreatedAt` and `UpdatedAt` as a pair. Each must use non-null `time.Time` or `temporal.DateTime`; column tags keep their existing mapping. The pair enables automatic timestamps by convention. `timestamps=false` leaves these fields ordinary; `timestamps=true` requires a valid pair. A lone field does not enable the pair implicitly. Generated notices identify the managed behavior beside the actual fields and draft setters.
- Creation supplies `CreatedAt` only when omitted and always sets `UpdatedAt`. Updates always set `UpdatedAt`, including an otherwise empty draft. Apply these conventions after before-write hooks and before field mutators, then validate final stored values. An explicit creation time remains subject to its ordinary codec and mutator. Automatic time fields require the same input and stored type when a custom mutator exists; Foundry cannot invent a distinct custom input.
- Sample the owning application clock once for an executed write attempt, normalize UTC and truncate that framework-produced instant to PostgreSQL microsecond precision. Manually supplied values retain ordinary strict codec validation. Creation/update timestamps from one attempt use the same sampled instant. Do not sample during query/draft construction, reads, invalid declaration handling or an empty bulk operation.
- Database modules inherit `foundation.Runtime.Clock()` before startup. Standalone pools default to `clock.System`; a database construction option can explicitly override the source. Keep clock dependencies separate from connection bounds and adapter credentials. Sessions, transactions, savepoints and custom transactor wrappers retain the actual owner's source. Real cancellation/acquisition/cleanup deadlines remain independent of application time. No process-global clock or new application service registry is introduced.
- Explicit bulk inserts apply the same conventions without per-model observers and share one clock sample per statement. An upsert's update action copies the destination's already-normalized proposed `UpdatedAt`, including database trigger effects; it does not run that field's Go mutator twice. Preserve policy validation, duplicate/foreign assignment rejection, reusable inputs and `DO NOTHING` semantics. Empty or invalid conflict policies do not become valid merely because an automatic timestamp could be added.
- Effective assignments from these conventions feed the existing change-set capture. Preserve original caller drafts. A veto, failed codec or invalid clock instant rolls back its transaction/savepoint. Database defaults and returned trigger values remain reflected in stored snapshots. Physical deletion does not run timestamp assignments. Soft deletion/restoration will reuse this clock/assignment path while retaining their separately specified event order.
