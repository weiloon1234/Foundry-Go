# Migrate to Foundry-Go v0.2

Foundry-Go v0.2 reduces compile footprint across validation, HTTP, and the ORM
by replacing large generic method sets with methodless handles, configuration
options, and package functions. Replaced methods are removed with no shims or
compatibility aliases.

This guide describes how to migrate an existing v0.1 application using the
type-aware migration tool, resolve manual inventory findings, regenerate
contracts, and apply the new API patterns.

## Migration workflow

The migration uses the type-aware Foundry-Go v0.2 codemod, which inspects your
code against its installed v0.1 dependency, resolves AST and type information,
and performs safe rewrites.

The codemod is available through
`go run github.com/weiloon1234/Foundry-Go/cmd/foundry@v0.2.0 codemod` (pinned to
v0.2.0) and is removed from later releases. The codemod must run **before**
bumping `go.mod`, because it resolves old v0.1 call sites against the app's
current v0.1 dependency.

Run the verified sequence below from your application's module root:

### 1. Run a dry run with your v0.1 dependency

Keep your application's `go.mod` dependency at **v0.1** while running the
codemod. From your application repository root:

```sh
GOWORK=off go run github.com/weiloon1234/Foundry-Go/cmd/foundry@v0.2.0 codemod ./...
```

The codemod analyzes active packages and prints each finding with its `file:line`,
status, and proposed edit. If your consumer is in a subfolder or external path,
pass `--dir /path/to/consumer`.

### 2. Handle the unresolved inventory in v0.1-valid form

Restructure unresolved findings in **v0.1-valid** form until the dry run reports 0;
`--apply` refuses while any remain.

In real migrations across multiple applications (e.g. Starter had 57 unresolved
findings, ooo about 445 lines), typical patterns include:

- **Capture side-effecting or non-addressable receivers in locals:** If an
  expression or option argument contains a function call, channel receive, or
  non-addressable receiver, evaluate and store it in a local variable first so
  evaluation order and receiver addressability are explicit.
- **Replace method values with explicit closures:** Method values such as
  `r.Check` or `c.Set` passed to custom helpers require an explicit closure
  capturing the receiver once. During this inventory step, the closure must
  still call the v0.1 method. The codemod later rewrites that call to
  `validation.Check`; calling the v0.2 function before the dependency upgrade
  would make the input invalid for analysis.
- **Give helper parameters concrete column types instead of interfaces:** Give
  helper parameters concrete column types instead of interfaces (for example, a
  username rule taking `orm.Text[...]` instead of a generic or custom column interface).
- **Pointer or promoted receivers:** Dereference or snapshot the handle
  explicitly before invoking package functions.
- **Consumer interfaces expecting removed methods:** If application code
  defined interfaces matching old receiver methods (for example expecting
  `Rules(...Rule[V]) Rule[T]`), update the interface to accept a package function
  or pass a typed callback.
- **Custom or indirect model binding:** Transports must implement
  `modelbinding.Transport` directly. Transports intentionally binding after
  validation must opt into `http.AfterValidation`.
- **Unsupported replay combinations:** Idempotency with optional actors,
  signed optional actors, or custom replay transports is not supported;
  use supported concrete replay descriptors.

### 3. Apply the codemod

Once unresolved findings are addressed and the dry run reports 0 findings:

```sh
GOWORK=off go run github.com/weiloon1234/Foundry-Go/cmd/foundry@v0.2.0 codemod --apply ./...
```

The tool atomically updates modified files and formats them with `go/format`.
Generated files (`*_foundry.gen.go` and files containing generated headers) are
intentionally untouched by the codemod.

### 4. Upgrade dependency and tidy

Update `go.mod` to reference Foundry-Go v0.2 and tidy modules; the `tool`
directive in `go.mod` now resolves to v0.2.0:

```sh
go get github.com/weiloon1234/Foundry-Go@v0.2.0 && go mod tidy
```

### 5. Regenerate and verify

Run code generation with the upgraded tool, plus the application's contract
export or check (if any), then run build, vet, and the application's gate:

```sh
go tool foundry generate
go build ./...
go vet ./...
```

## Why per-kind ORM operators (`orm.Eq` note)

In ORM Design 2, column operators use per-kind function names (such as
`orm.TextEq`, `orm.NumberEq`, `orm.KeyEq`, `orm.EnumEq`) rather than a single
unified `orm.Eq(col, val)`.

During design evaluation, a single generic `orm.Eq` was prototyped (both as the
Design 1 sealed witness pattern and the D2-Eq variant). In benchmark tests,
a single generic `Eq` **failed the runtime performance gate**:

- Chain build benchmarks regressed by **+25.4% to +28%** in median execution
  time due to generic witness wrappers, dynamic dispatch, and missed compiler
  inlining.
- Go's type system does not support function overloading, and type union
  constraints cannot provide common field selectors across methodless column
  structs (`textColumnData`, `nullableColumnData`, `key`, etc.) without value
  boxing or runtime type switches, which violate framework zero-allocation and
  type-safety guarantees.

In contrast, Design 2 methodless handles with concrete per-kind operators
passed all seven runtime gates with zero extra allocations, reduced marginal
functions per model by **79.8%** (739 → 149), and lowered compiler RSS by
**74.9%**.
