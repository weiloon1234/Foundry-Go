# Named services and defaults

`infrastructure.Configure` assembles PostgreSQL, Redis, disks and caches from
concrete settings. It reuses the existing providers and lifecycle. The
[application builder](application-bootstrap.md) uses this same assembly layer and
passes its typed services into ordinary domain constructors. The following API
is also available directly for advanced composition.

```go
settings := infrastructure.DefaultSettings()
settings.Cache.Stores = infrastructure.CacheStores{
    "default": infrastructure.DefaultCacheSettings(),
    "reports": infrastructure.DefaultCacheSettings(),
}
plan, err := infrastructure.Configure(settings)
if err != nil { return err }
app, err := plan.Register(foundry.New()).Build(ctx)
if err != nil { return err }
return app.Start(ctx)
```

`services, err := foundation.Resolve(app.Services(), infrastructure.ServicesKey)`
returns constructor dependencies. `services.Cache()`, `services.Database()`,
`services.Disk()` and `services.RedisConnection()` select their configured defaults.
For a named instance use `services.Caches.Store(Reports)`,
`services.Databases.Connection(ReportingDB)`, `services.Storage.Disk(Uploads)` or
`services.Redis.Connection(QueueRedis)`. Declare those names as `cache.StoreName`,
`database.ConnectionName`, `storage.DiskID` and `redis.ConnectionName`. One family's
name cannot select another family. Ordinary domain constructors receive the
resolved concrete dependency; they do not use a context service bag.

An empty collection disables its family. Each nonempty collection requires its
configured default (initially the name `default`). The default aliases an existing
instance: there is no extra default pool and no selection based on map order.
Explicit unknown names fail. Empty Redis/database references in dependent service
settings use that family's configured default. Independent applications own
independent resources, even when built from the same immutable plan.

Default-selection errors identify the generated setting path, such as
`database.default` or `storage.default`, while retaining `fault.Missing` for an
unconfigured default and `fault.Invalid` for an invalid name. The path is relative
to `infrastructure.Settings`; configured values are not included in these errors.

## Typed configuration tables

Application `//foundry:config` settings may contain `infrastructure.Settings` as a
normal nested field. Framework settings and their keys are generated by the same
configuration generator as consumer settings. Named collections use the shared
`config.DecodeTable` codec and generated element schemas:

```toml
[services.database.connections.default.primary]
host = "db.example.test"
port = 5432
database = "example"
user = "example"
tls = "verify-full"

[services.database.connections.default.primary.pool]
connect_timeout = "5s"

[services.redis.connections.default]
host = "redis.example.test"

[services.cache.stores.default]
driver = "redis"

[services.cache.stores.reports]
driver = "memory"

[services.storage.disks.default]
driver = "local"

[services.storage.disks.default.local]
root = "/srv/example/storage"
```

Each supplied collection replaces the complete earlier collection. Every named
entry starts with its adapter defaults, then applies the supplied nested fields.
Durations use strings (`"5s"`); secrets retain `secret.String`; unknown fields,
duplicate JSON keys, invalid widths and oversized/deep input fail. Environment
variables for a collection contain the same JSON object representation, e.g.
`APP__SERVICES__CACHE__STORES`; individual dynamic names do not create environment
variables or generated Go identifiers. Typed `ConfigKeys().…Set` overrides keep
the entire concrete collection type. Connection/credential provenance is redacted.
Do not serialize settings to build new input: secret serialization is redacted.

Provide actual secrets through operator-controlled inputs. An AWS chain can read
its standard credential sources; other adapters do not discover credentials from
process globals. Configuration does not automatically load `.env` files.

## Ownership and bounds

Configure/Build validate without connecting, opening storage roots or running
migrations. Start acquires resources and installs cleanup before fallible boot
work. Borrowers drain before owners. Pools retain the existing PostgreSQL
primary/read topology and transaction identity. Total configured connection
ceilings are bounded, including Redis pub/sub capacity. Redis borrowers share
explicitly referenced clients; namespaces, not Redis database numbers, define
pub/sub isolation.

Local storage uses its managed object format and requires an existing empty or
previously owned root. S3 and R2 use the common disk contract. Named credential
sources use `credentials.Settings`; `Cloud.Credentials` selects one. R2 requires
an explicit non-chain source. `infrastructure.WithCredentials` supplies a borrowed
rotating `credentials.Provider`; keep it alive until application shutdown.
`Config.WithCredentials` is also available on S3 and SES without native SDK types.
Existing native customization remains available through the advanced adapter APIs.

## Cache choices

| Driver | Persistence | Tags / namespace invalidation | Counters / expiry | Distributed fills |
| --- | --- | --- | --- | --- |
| memory | Process lifetime | Yes | Yes | No |
| redis | Server policy | Yes | Yes | Optional, same Redis lease authority |
| file | Owned local filesystem | No | Yes | No |
| postgres | Explicitly migrated table | No | Yes | No |

`CacheSettings.Require` checks needed capabilities during assembly. File and
PostgreSQL provide expiry-aware atomic add/counters, existence and expiry updates.
They do not emulate tags, atomic batch removal or distributed fill coordination.
Ordinary Remember coalesces calls within one Store. Redis distributed fills also
require `Require.DistributedFills` and matching lease/cache namespaces.

Automatic cache namespaces append the store name to the configured application
namespace; explicit namespaces allow deliberate sharing. The new persistent
backends serialize atomic mutations and capacity checks. File operations use
process locks and atomic publication under `os.Root`; network filesystems are
unsupported. Their capacity checks scan bounded entries, so Redis is preferable
for high-throughput shared caching. File syscalls cannot be interrupted; lock
contention honors context cancellation. Errors after publication may hide an
applied write, and adapters never retry it automatically.

File and PostgreSQL limits include retained expired records. Call bounded `Prune`
explicitly to reclaim expiry; file prune also removes orphan temporary files.
All processes sharing a physical cache must use matching bounds and synchronized
clocks. PostgreSQL expiry has database timestamp precision. `plan.Migrations()`
returns database/schema targets for explicit cache migrations. No migration runs
at application boot, and no cleanup resets a database or touches unrelated data.
